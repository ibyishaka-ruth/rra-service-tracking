# RRA Taxpayer Service Feedback

React + Vite interface for receptionist check-in/service routing and taxpayer feedback.

## Run locally

1. Start the Spring Boot backend. The Vite development proxy defaults to `http://localhost:8082`.
2. In this directory, run:

   ```powershell
   npm run dev
   ```

3. Open the local URL printed by Vite (usually `http://localhost:5173`).

To use a backend on a different port, set `VITE_API_TARGET` before starting Vite:

```powershell
$env:VITE_API_TARGET = "http://localhost:8080"
npm run dev
```

## Reception workflow

The reception desk validates a nine-digit TIN, loads active entries from the RRA routing catalog, and searches service names and common keywords. If the TIN is not in the local prototype database, reception creates a minimal taxpayer record using that TIN, then:

1. Create a visit with `POST /api/v1/visits`.
2. Create a service request with `POST /api/v1/service-requests`.
3. Show the generated service request number and its configured destination department.

This prototype registration stores only the entered TIN. It does not verify that TIN against RRA records, issue a TIN, or fetch a taxpayer name or phone number. Replace it with the official RRA profile integration when that API is available. The service request number is generated by the database when the backend saves the request; the visit/check-in number is a separate generated ID. The receptionist sees the configured department and sub-unit. Priority is retained as catalog metadata but is not used to rank taxpayers or service requests; all requests follow the same handling policy.

New service requests start with `PENDING`. Recording unfinished work keeps the request pending and may include a reason; only recording `COMPLETED` closes it. Feedback remains available only after completion. Role-based staff assignment and dashboards are planned next; authentication, taxpayer-profile lookup, and SMS delivery are not connected yet.

The catalog in `backend/src/main/resources/rra-service-routing.json` is the supplied initial routing list. Confirm department and sub-unit assignments with RRA before production use. Its stable `srv_###` routing code is distinct from the numeric database ID used by existing API relationships.

The supplied catalog includes a new-TIN registration service, but the prototype cannot issue a TIN. Handling applicants who do not yet have a TIN requires a separate registration/intake flow.

## Feedback workflow

The feedback view verifies the service request with `GET /api/v1/service-requests/{id}`, then submits it with `POST /api/v1/feedback`. The backend stores feedback in PostgreSQL's `feedback` table, linked to the service request. It remains responsible for validating completed status and preventing duplicate feedback.
