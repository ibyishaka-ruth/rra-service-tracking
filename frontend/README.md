# RRA Taxpayer Service Feedback

React + Vite interface for receptionist check-in/service routing and taxpayer feedback.

## Run locally

1. Start the Spring Boot backend. The Vite development proxy defaults to `http://localhost:8082`.
2. In this directory, run:

   ```powershell
   npm run dev
   ```

3. Open the local URL printed by Vite (usually `http://localhost:5173`).

To use a backend on a different port, set `VITE_API_TARGET` before starting Vite:

```powershell
$env:VITE_API_TARGET = "http://localhost:8080"
npm run dev
```

## Local data storage

Application records are stored by the Spring Boot backend in PostgreSQL, not in the browser. Unless `DB_URL` is overridden, the backend connects to the local `rra_taxpayer_service` database on port `5432`; `DB_USERNAME` and `DB_PASSWORD` can also be configured through environment variables. The backend uses Hibernate schema updates, so restarting the frontend does not clear saved taxpayers, visits, requests, or feedback. The in-memory H2 database is used only for automated backend tests.

The service-routing JSON is loaded at backend startup and updates the department and service catalog; it does not recreate taxpayer visits or service requests. If saved records appear missing, first confirm PostgreSQL is running and that the backend is using the same `DB_URL` and database as before. A different database URL or database instance will show a separate set of records.

## Reception workflow

The reception desk validates a nine-digit TIN, loads active entries from the RRA routing catalog, and searches service names, departments, sub-units, and common keywords in one service picker. If the TIN is not in the local prototype database, reception creates a minimal taxpayer record using that TIN, then:

1. Create a visit with `POST /api/v1/visits`.
2. Create a service request with `POST /api/v1/service-requests`.
3. Show the generated service request number and its configured destination department.

This prototype registration stores only the entered TIN. It does not verify that TIN against RRA records, issue a TIN, or fetch a taxpayer name or phone number. Replace it with the official RRA profile integration when that API is available. The service request number is generated by the database when the backend saves the request; the visit/check-in number is a separate generated ID. The receptionist sees the configured department and sub-unit. Priority is retained as catalog metadata but is not used to rank taxpayers or service requests; all requests follow the same handling policy.

New service requests start with `PENDING`. The department front-desk view lists requests in a filterable table across departments. Selecting a row opens the full request details and assignment/outcome controls. Its department filter includes departments configured in the active service-routing catalog as well as departments present in existing requests. The queue loads when opened and then receives change notifications through Server-Sent Events, so it does not poll or rerender every few seconds. Assignment changes its status to `IN_PROGRESS`; the dashboard shows the number of active requests assigned to each known staff name as a workload indicator. This is only a count of work tracked in this prototype, not a live staff roster, calendar, or full workload system. Staff can mark their active request `COMPLETED`, which enables taxpayer feedback, or return it to the pending queue with a reason. Feedback remains available only after completion. Staff authentication and an approved staff directory, taxpayer-profile lookup, and SMS delivery are not connected yet.

The catalog in `backend/src/main/resources/rra-service-routing.json` is the supplied initial routing list. Confirm department and sub-unit assignments with RRA before production use. Its stable `srv_###` routing code is distinct from the numeric database ID used by existing API relationships.

The supplied catalog includes a new-TIN registration service, but the prototype cannot issue a TIN. Handling applicants who do not yet have a TIN requires a separate registration/intake flow.

## Feedback workflow

The feedback view verifies the service request with `GET /api/v1/service-requests/{id}`, then submits it with `POST /api/v1/feedback`. The backend stores feedback in PostgreSQL's `feedback` table, linked to the service request. It remains responsible for validating completed status and preventing duplicate feedback.

The admin feedback review view uses `GET /api/v1/feedback` to list submissions with their service and department, supports search and filters, reports the average rating, and exports the filtered rows to CSV. Feedback is displayed in a compact table; selecting a row reveals its comment and full details. It loads when opened and can be updated with its manual Refresh button. This prototype view is not protected by authentication or authorization; do not expose it publicly or use it with production feedback data until role-based access controls are implemented.
